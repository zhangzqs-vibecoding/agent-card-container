状态：**执行中，作为后续工作包入口**
日期：2026-07-15（Asia/Shanghai）  
适用基线：`develop` / `d8e6da3`

## 1. 目标

下一阶段的目标不是继续堆叠底层框架，而是尽快形成一个用户可以反复使用的完整闭环：

> 用户描述需求 → 云端 Agent 生成卡片 → 客户端预览并确认权限 → 安装到工作区或独立窗口 → 离线运行 → 修改、升级和回滚。

当前后端生成、签名、持久化和 worker 可靠性已经具备 Linux/headless 基础。后续应优先验证真正影响产品成立的三件事：生成质量、桌面使用体验和卡片生命周期。

### 1.1 当前进展快照

截至适用基线，以下工作已经形成可复核的 Linux/headless 证据：

- NativeCard 真实 DeepSeek 生成、确定性校验、签名、下载和独立复核链路。
- PostgreSQL/MinIO 持久化、服务重启恢复、成对备份恢复和远程制品下载门禁。
- worker 原子入队、租约 heartbeat、owner fencing、有限重试、取消传播和发布幂等。
- CodeCard 受控 builder、固定评测合同、Linux Chromium 离线运行、localhost RPC 和签名发布自动化。
- 工作区 12 列网格、拖动、缩放、碰撞避让、300ms SQLite 持久化、重启恢复和失败回滚。
- 云端同卡迭代已经完成 `baseCardId`/`baseVersionId` 合同、所有权校验、可信旧制品读取、Agent 基线注入、同 `cardId` 新版本、严格 display version 和 PostgreSQL/MinIO 恢复；客户端升级与回滚仍在实施。

这些结论不替代 Windows 实机证据。WebView2、多窗口、悬浮、DPI、中文 IME、多显示器和机器重启恢复仍保持 `DEVICE NOT RUN`。

## 2. 产品定位

本项目定位为“Agent 驱动的桌面卡片容器”，而不是通用低代码平台或完整 IDE。

- NativeCard：安全、稳定、跨平台一致，适合信息展示、表单和标准交互。
- CodeCard：允许本地 JavaScript、离线逻辑和复杂交互，适合小游戏、画板、可视化及本地工具。
- Flutter Shell：负责工作区、窗口、安装、权限、状态和平台适配。
- Go Cloud：负责需求澄清、Agent 编码、受控构建、签名、发布和版本管理。
- Capability Broker：是两类卡片访问系统能力的唯一入口。

短期不做卡片市场、多人协作、移动端完整适配、第三方插件 SDK 和 Agent 自主操作用户桌面。这些方向只有在核心闭环稳定后再评估。

## 3. 优先级

### P0：让当前链路可在真实 Windows 上验收

这是最高优先级，因为桌面窗口、WebView2、DPI、IME 和离线恢复无法由 Linux CI 证明。

交付内容：

- 用 Windows 11 x64 参考设备完成 NativeCard 生成、下载、验签和安装。
- 验证主工作区、独立窗口、置顶悬浮窗口三种 Surface。
- 验证 100%/150% DPI、多显示器、中文 IME、焦点和窗口恢复。
- 验证断网重启后已安装 NativeCard 仍可使用。
- 所有证据绑定 commit、Flutter、Windows、WebView2 和制品 hash。

完成标准：P0-C 设备矩阵全部执行；未执行项保持 `NOT RUN`，CI 构建不能替代设备证据。

### P1：完成 CodeCard 真实模型与 Windows 链路

CodeCard 是产品差异化能力，应作为下一项主要研发工作。

受控 builder 和 Linux/headless 自动化已经完成；剩余交付内容：

- Flutter 通过桌面 WebView2 加载本地 Runtime Server 提供的制品。
- 卡片内部 JavaScript 通过 localhost HTTP RPC 调用 Capability Broker；RPC 使用随机卡片域、短期会话令牌、方法白名单和参数校验。
- 已安装资源包、本地状态和必要运行时元数据持久化，断网与应用重启后可用。
- WebView 崩溃只隔离单张卡片，不拖垮主应用。
- 使用临时模型凭据执行预先冻结的 20 例真实 CodeCard 质量门，并记录质量、调用次数、token 和成本证据。

质量门槛必须在真实模型评测前锁定。建议第一版固定 20 个用例，覆盖自由画板、小游戏、数据可视化、复杂交互、纯离线工具各 4 个；记录首次通过率、修复后通过率、平均调用次数、token 和估算成本。具体通过率应在独立 P1-C 设计评审中确认，不能测试后再调整门槛。

### P1：补齐卡片实例和版本生命周期

该工作可与 CodeCard 的平台无关部分并行，但 Windows 交互结论必须等待设备验证。

交付内容：

- 在工作区、独立窗口和悬浮层之间移动，保持实例状态。
- 复制、删除、卸载以及“保留数据/删除数据”的明确选择。
- 基于已有卡片发起修改，稳定复用 `cardId`，产生新 `versionId`。
- 升级前展示能力差异和状态 schema 兼容性。
- 同 schema 复用状态；异 schema 先备份，再由用户选择保留旧版或重置安装。
- 升级失败自动保留旧版本和旧状态，支持显式回滚。

MVP 不执行模型生成的状态迁移代码，避免把不可信代码引入本地数据升级路径。

### P1：可观测性和运营最小闭环

现有请求日志和 readiness 需要扩展为可定位生成失败的最小信号，但暂不引入大型 tracing 平台。

交付内容：

- 记录队列深度、生成成功率、各阶段耗时、attempt 分布、租约过期、错误类别、token 和估算成本。
- 客户端展示可执行的错误类型：配置、认证、网络、生成、校验、构建、发布、下载、验签、安装。
- 使用 request/session/job/card/version 关联 ID 串联日志。
- 提供最小管理查询，能够定位卡住任务和失败阶段，但不暴露 prompt、模型输出、密钥、Cookie、DSN 或上游正文。

### P2：认证、配额和可信发行

在公开测试前完成，不阻塞内部闭环验证。

交付内容：

- 用 OIDC 或等价方案替换开发 Token，客户端凭据进入系统安全存储。
- 按用户设置并发数、调用次数、token、构建时长和存储配额。
- 增加限流、审计、滥用检测和费用硬上限。
- Windows Authenticode、正式安装器、WebView2 缺失引导、升级与卸载清理。
- Windows 闭环稳定后再推进 macOS WKWebView、App Sandbox、签名和 notarization。

## 4. Agent 编码方案

当前阶段不建议为了“像 Agent”而引入 Eino、LangGraph 或 Claude Agent SDK。现有 Go 编排器已经具备需求快照、模型调用、校验、修复循环、worker 和发布边界，继续使用显式状态机维护成本最低，也更容易限制成本和权限。

Agent 应保持以下边界：

1. 输入是冻结后的用户需求、目标 runtime、模板说明和允许能力集。
2. 模型只能在候选能力集合内请求能力，不能自行扩大权限。
3. NativeCard 输出结构化协议；CodeCard 输出限定文件集合，不输出或执行 Shell/Dart/本机脚本。
4. 每次生成使用固定的调用次数、token、时间和构建预算。
5. 校验失败只把稳定错误类别和必要定位信息返回修复循环。
6. 生成、构建、签名和发布彼此分层，模型无法接触签名私钥或对象存储凭据。

只有当出现多个可独立调用的工具、复杂分支规划、长周期任务恢复或多 Agent 协作需求时，再评估引入 Agent 框架。届时应通过窄接口替换 `agent` 内部实现，而不是让框架渗透到 HTTP、worker 和发布模块。

## 5. 推荐实施顺序

| 顺序 | 工作包 | 产出 | 依赖 |
|---:|---|---|---|
| 1 | P1-A 客户端升级与回滚 | 能力差异、状态保护、原子切换和回滚 | 已完成的云端同卡迭代 |
| 2 | P1-A 实例生命周期 | 复制、删除、卸载及数据保留选择 | 已完成的布局持久化 |
| 3 | P1-C 真实 CodeCard 质量门 | 20 例真实模型质量和成本证据 | 临时模型凭据与价格配置 |
| 4 | P0-C/P1-C Windows 设备闸门 | NativeCard、CodeCard、三类 Surface 和离线证据 | 固定测试服务、Windows 设备 |
| 5 | 可观测性与配额 | 可运营、可控成本的测试环境 | 真实生成数据 |
| 6 | P2 Windows 可信发行 | 可供外部测试的签名安装包 | P0/P1 闭环通过 |

每个工作包必须单独建立实施计划，遵循 TDD，小步提交，并在结束时生成验证证据。该文档只定义顺序和边界，不替代各工作包的详细计划。

## 6. 最近三个可执行动作

1. 完成 Flutter 端同卡升级、能力差异确认、状态备份和失败回滚。
2. 完成实例复制、删除、卸载及数据保留选择，并复用同一状态备份模型。
3. 准备固定测试服务和 Windows 候选构建，在同一 commit 上执行 NativeCard 与 CodeCard 的真实设备矩阵；有临时模型凭据和价格配置时同步运行 CodeCard 20 例质量门。

上述每项都应建立或沿用独立实施计划，先写失败测试，再做最小实现，最后生成与精确 commit 绑定的验证证据。

## 7. 暂不推进

- 不引入 Kafka、Temporal 或额外微服务拆分。
- 不允许模型直接运行 Shell、本机脚本、Dart 或未签名制品。
- 不把 WebView 页面直接暴露到公网，也不开放任意 URL 导航。
- 不做任意 npm 在线安装；依赖必须来自锁定、审计过的受控集合。
- 不用“能打开窗口”代替 WebView2、DPI、IME、离线和恢复的设备验收。
- 不在核心闭环验证前建设卡片市场、社交、付费分成或第三方生态。

## 8. 阶段性成功标准

达到以下状态即可开始小范围内部试用：

- 用户能稳定生成至少一类 NativeCard 和一类 CodeCard。
- 两类卡片都能安装到主工作区，并可切换到独立窗口。
- CodeCard 的本地 JavaScript、storage 和受控 RPC 在断网重启后正常。
- 卡片升级失败不会破坏旧版本或用户状态。
- 后端任务可重试、可取消、无重复发布，并能从日志定位失败阶段。
- Windows 设备矩阵有绑定同一候选 commit 的证据。
- 真实模型成本有硬上限，仓库、日志和制品中不存在敏感凭据。
